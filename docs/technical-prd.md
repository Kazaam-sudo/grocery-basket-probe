# Technical PRD: первый спринт — адресная корзина «Перекрёстка»

**Статус:** утверждённый каркас для технической проверки.  
**Рынок:** Москва и Московская область.  
**Срок:** две недели.  
**Не является:** юридическим заключением или разрешением на автоматизированный доступ к любому сайту.

## 1. Цель и решение, которое принимает спринт

Проверить, можно ли **без обхода технических ограничений** и с низкой частотой запросов повторяемо получить публичные адресные предложения «Перекрёстка» для одной реальной тестовой корзины.

К концу спринта должно быть возможно выбрать один из трёх заранее утверждённых тестовых адресов, найти до 20 позиций тестовой корзины, сохранить наблюдения и выгрузить JSON/CSV со следующими полями:

`товар / упаковка / цена / тип цены / наличие / URL / источник / зона или магазин / время проверки`.

Спринт не доказывает жизнеспособность продукта на трёх сетях и не реализует интерфейс для покупателей.

## 2. Scope

### Входит

- реестр трёх тестовых адресов без публикации полного адреса в логах;
- source investigation публичной витрины;
- read-only контракт коннектора и только один коннектор после положительной разведки;
- до 100 массовых SKU для проверки покрытия, 20 — для acceptance demo;
- PostgreSQL-модель источников, предложений и временных наблюдений;
- низкочастотный запуск, структурированные логи, экспорт JSON/CSV;
- изолированная обработка ошибок одной карточки.

### Не входит

- пользовательские аккаунты, SMS, карты лояльности, токены мобильных приложений;
- CAPTCHA bypass, прокси для обхода ограничений, ротация fingerprint, повышенные ретраи;
- заказ, оплата, добавление в корзину ритейлера;
- изображения, длинные описания, отзывы, персональные скидки;
- сопоставление товаров между сетями, оптимизатор корзины, Telegram-бот и UI.

## 3. Требования

### Функциональные

1. Система хранит тестовые адреса как внутренние IDs, fingerprint и разрешённый контекст источника; полный адрес не пишется в логи.
2. Коннектор устанавливает контекст адреса только разрешённым публичным способом или завершает запуск статусом `blocked`.
3. Коннектор ищет SKU и нормализует доступные факты в `SourceOffer`.
4. Каждое наблюдение неизменно сохраняет ID исходного товара, URL, время, цену, тип цены, наличие, размер упаковки и доступный ID зоны/магазина.
5. Повторный запуск создаёт новую `price_observation`, но не дублирует `source_product`.
6. Ошибка одного SKU сохраняется в `connector_errors` и не прекращает остальной запуск.
7. Экспорт содержит только факты, необходимые для аудита результата.

### Нефункциональные

- read-only; никаких POST-операций к ритейлеру;
- базовый лимит — не более 6 запросов в минуту на источник до подтверждения допустимой частоты;
- кеширование и exponential backoff только для временных сетевых ошибок, без попыток обхода 403/429;
- при CAPTCHA, SMS, login wall, 403/429, явном запрете условий или необходимости закрытого токена запуск прекращается;
- один SKU не должен блокировать весь прогон;
- исходные ответы не хранятся по умолчанию; при необходимости — минимальный безопасный sample с коротким retention и без персональных данных;
- аудит: run ID, версия коннектора, адресный context ID, счётчики успехов/ошибок и причина остановки.

## 4. Сущности

Схема детализирована в [data-model.md](data-model.md). Ключевая грань: `source_product` — относительно постоянная карточка источника, `offer` — её предложение в зоне/магазине, `price_observation` — неизменный факт во времени.

## 5. API прототипа

Публичный API нужен только для локальной демонстрации и не должен запускать неограниченный сбор.

| Method | Route | Назначение |
|---|---|---|
| `GET` | `/health` | liveness процесса, без обращения к источнику |
| `POST` | `/runs` | запуск утверждённой корзины для тестового address ID |
| `GET` | `/runs/{id}` | статусы, счётчики, причина stop/blocked |
| `GET` | `/runs/{id}/export?format=csv|json` | отчёт по наблюдениям |

`POST /runs` добавляется только после source investigation, обязательные ограничения: allow-list test address IDs, ограничение SKU, один активный run на источник, rate limiter.

## 6. Ошибки и безопасность

| Сигнал | Поведение |
|---|---|
| CAPTCHA/SMS/login/закрытый токен | `blocked`, без повторной попытки |
| HTTP 403/429 | `blocked`, сохранить заголовки/код без секретов, отключить источник |
| Неизвестная схема | `degraded`, сохранить безопасный schema fingerprint, не публиковать цену |
| Таймаут/5xx | ограниченный retry, затем ошибка конкретного SKU |
| Не найден товар | `not_found`, run продолжается |

Секреты не коммитятся. Полные адреса, cookies, заголовки авторизации и ответы с персональными данными не попадают в логи, тестовые фикстуры или отчёты.

## 7. Наблюдаемость и тесты

Метрики: число запросов, запросы в минуту, success/not-found/error/blocked, доля цен, доля известных упаковок, возраст наблюдения, количество изменений схемы. Alerting в этом спринте может быть локальным отчётом run; внешний Sentry не требуется до положительного Go.

Тесты: unit для нормализации и контрактов, интеграционные для БД, заранее сохранённые разрешённые fixtures, acceptance run на 20 SKU. В тестах запрещены live-вызовы к ритейлеру.

## 8. Готовность и stop-критерии

### Go

- установлен публичный адресный контекст для всех трёх адресов;
- 80%+ тестовых 20 SKU находятся хотя бы один раз;
- цена, упаковка и URL есть у 95% найденных товаров;
- два запуска создают новые observations и дают объяснимые изменения;
- нет CAPTCHA, SMS, закрытого аккаунта, регулярных 403/429 и нарушения условий;
- один сбой карточки изолирован.

### Pivot

Технически данные доступны, но отсутствует надёжное поле наличия/адресной зоны или стабильный публичный путь. Остановить разработку коннектора и перейти к официальному/партнёрскому фиду, агрегатору или ограниченному каталогу акций.

### Stop

Нужен обход защиты, чужие учётные данные, токен приложения, регулярные блокировки при низкой частоте, условия явно исключают выбранное использование либо невозможно привязать предложения к адресу.
